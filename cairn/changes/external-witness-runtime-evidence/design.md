## Context

Halo-record is useful because it separates three concerns that are easy to
collapse in agent evidence systems:

- integrity: the presented sequence has not been edited or reordered;
- completeness: an independent party previously saw a prefix of that sequence;
- capture strength: evidence recorded at the trust boundary is stronger than
  telemetry ingested after the fact.

Cairn has local deterministic receipts, evidence manifests, and optional public
signer/anchor metadata. Today those anchors are hashed metadata only and do not
carry verifier semantics. The new slice makes witness checkpoints first-class
bounded evidence while preserving Cairn's existing non-claim discipline.

## Decisions

### 1. Runtime records are subject-scoped chain entries

**Choice:** Define a Cairn-owned runtime action record with `subject`,
`record_id`, optional `parent_id`, `agent_identity`, `action`, `authorization`,
`capture_origin`, `input_identity`, `outcome_identity`, `integrity`, and
`non_claims` fields.

**Rationale:** Subject-scoping prevents one customer's, repository's, or release's
runtime evidence from being filtered out of a shared chain after the fact.
Per-subject chains also give downstream consumers a single chain root and head to
reason about without seeing unrelated subjects.

### 2. BLAKE3 remains the stack-owned identity hash

**Choice:** Cairn-owned runtime records and checkpoints use BLAKE3 over canonical
Cairn JSON, excluding the self hash field. Imported Halo/AARM-compatible records
may carry their declared SHA-256/RFC8785 identity as external metadata, but Cairn
computes its own BLAKE3 wrapper identity before using them in receipts.

**Rationale:** BLAKE3 is the stack default for content identity. Compatibility
metadata should not force Cairn's native receipt surfaces to switch algorithms.

### 3. Completeness is checkpoint comparison, not witness trust

**Choice:** The verifier compares presented chains against supplied checkpoint
artifacts and emits deterministic verdict classes such as `integrity_only`,
`witnessed_prefix`, `not_witnessed`, `subject_mismatch`, `truncated`, and
`altered_before_checkpoint`.

**Rationale:** Cairn can prove whether a checkpoint matches the presented chain.
It cannot prove that the checkpoint holder is independent, recognized, or legally
trusted. That decision remains outside the deterministic local verifier and must
be documented as a non-claim.

### 4. Capture origin is evidence strength, not an assertion upgrade

**Choice:** Records classify origin as `boundary_captured`, `ingested_telemetry`,
`wrapper_asserted`, or `unknown`. The verifier preserves the class and fails
closed only for malformed or policy-denied values; it never upgrades ingested or
unknown records to boundary-captured evidence.

**Rationale:** This mirrors the useful halo-record distinction between captured
and ingested evidence while keeping Cairn's role discipline honest.

### 5. Hash-only operation is a policy profile

**Choice:** Runtime records may omit human summaries and retain only stable input
and outcome hashes. If summaries are present, they must pass policy-owned bounded
content and redaction checks.

**Rationale:** Agent runtime evidence must be shareable across trust boundaries
without leaking prompts, credentials, raw tool arguments, raw paths, or customer
data. Hash-only records are the safest default for public evidence bundles.

### 6. Integration is additive and verifier-first

**Choice:** Add runtime evidence roles to agent evidence bundles and evidence
manifests only after the standalone chain/checkpoint verifier exists. Existing
bundle, manifest, replay, and release-readiness semantics remain authoritative.

**Rationale:** The runtime evidence chain should be optional evidence attached to
Cairn's existing release flow, not a replacement for current validators.

## Risks / Trade-offs

- A local checkpoint generated by the same operator improves auditability but not
  independent completeness. Docs and receipts must call this out.
- Supporting imported Halo/AARM-style records adds compatibility complexity; the
  first implementation should wrap external identities rather than reusing them
  as Cairn-native hashes.
- Runtime chains may be large. Public evidence bundles should carry compact
  chain summaries and artifact hashes, while full chains remain external
  artifacts verified by role.
